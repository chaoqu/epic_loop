Herdr Epic Loop

An epic-level loop for shipping a planned feature with coding agents. The strongest model writes the plan, the plan becomes a beads dependency graph, a mechanical orchestrator gives each ticket its own herdr worktree, a test-gated queue merges the results one branch at a time, a fresh-context reviewer closes the loop, and the epic lands as one pull request.

Isolation
One worktree per ticket, branched from epic/<id>. The worktree outlives its agent.
Integration
Serial fast-forward into epic/<id>, after a rebase and a green suite in the ticket worktree.
Parallelism
Two to four workers, and only for tickets whose owned paths the plan declares disjoint.
Judgment
The orchestrator is a program with no memory. It calls a model as a function at three decision points, each with a schema.
Review
Fresh context, the diff and the rules only, at most three rounds, exit at zero blockers.
Landing
One PR per epic under about 600 changed lines, otherwise stacked PRs per ticket.

The pipeline at a glance

Six stages, in order. Three are machine-only. At the other three a human is in the loop: the interview that produces the plan, the questions the orchestrator cannot answer from the plan, and the pull request.

1PlanFable 5.1 or Opus 5, after an interviewTickets with runnable acceptance criteria, owned paths, one-session size, and a parallel or serial mark.
2Epicbr bulk importOne epic, its children, and blocks edges only where an interface really depends on another ticket.
3Orchestratescript; Sonnet 5 workersClaim, worktree, brief, verify in a separate pane, merge one at a time, close.

The three changes that matter most

  • A hybrid worktree model. One integration branch per epic and one worktree per ticket, parallel only where owned paths are disjoint, with a serial merge queue that reruns the tests before every fast-forward. The orchestrator never resolves a conflict; the authoring worker does, in the same worktree.
  • The orchestrator is a program, not an agent. Every pass re-derives state from br, git and herdr, never from memory. A model is called as a stateless function at exactly three decision points, each with a bounded input and a schema. Everything else is a rule.
  • Verification the worker cannot argue with. Acceptance criteria live in the ticket. The orchestrator reruns the tests in its own pane. The diff must stay inside the owned paths. Existing tests may not be modified or disabled.

Branch topology

Worktrees isolate files, not decisions. Two workers can each pass their own tests and still disagree about an interface, which is why coupled tickets run serially and the integrated branch gets its own review round.

  • Single-writer paths. Shared migrations, generated code and shared contracts each belong to exactly one ticket per epic. Every other ticket that needs them declares a blocks dependency on that ticket.
  • The integration branch starts with a marker. Its first commit is empty and exists nowhere on main, so "this worktree belongs to the epic" is a git fact: its HEAD descends from the marker. Which ticket it is comes from the ticket/<id> branch name, or from the ticket named in the worker's report file. Where the worktree lives on disk is never consulted, so a worktree an agent made for itself is still found, and one that matches no ticket is flagged and never merged.
  • The integration branch has a worktree too. Created at start, it is where every fast-forward happens and where the integration check runs after each one, so the integrated code is always checked out somewhere the app can be brought up. Only the loop touches it, and only by fast-forward, or by rolling back after a failed integration check.
  • Worktrees persist. A worktree outlives its agent. Conflicts and retries go to a fresh worker in the same worktree, which resumes from the commits plus the ticket notes.
  • Two to four in parallel, no more. Above that the bottleneck is human review, and at five parallel agents conflict resolution has been measured at 30 to 50 percent of agent time.
  • Every worktree can run the app. Each checkout derives its own ports for the app's services, so parallel worktrees do not fight over ports.
  • Serial is the fallback, not a failure. Fresh context per ticket comes from spawning a new agent either way. Running coupled tickets one after another loses only wall clock.

1Plan

The planner interviews first, following the product-first rule and /grill-intent, then writes the plan. The plan is accepted only when every ticket carries four things, because everything downstream leans on them.

  • Runnable acceptance criteria. A command or check the orchestrator can execute, not a sentence the worker interprets.
  • An owned-paths list. The directories this ticket may change. The merge queue uses it as a hard boundary on the diff.
  • One-session size. The ticket finishes inside one worker context. Anything larger is split before the epic is created.
  • A parallel or serial mark, with the blocks dependencies that justify it.

The fields each ticket carries into beads. The bulk-import markdown shape comes from br create --help; these are the fields, not the syntax.

# one ticket in the plan
title:        Port the snapshot append step to DCM
type:         task            priority: 1
parent:       <epic-id>
deps:         blocks:<shared-migrations ticket>
labels:       parallel, module:dcm
owned_paths:  services/<module>/, docs/spec/<module>/
acceptance:
  - [ ] <test command from the module CLAUDE.md> passes in the worktree
  - [ ] git diff --stat epic/<id> touches only the owned paths
  - [ ] no existing test file modified or disabled
size:         one session
notes:        interface this ticket exposes, and who consumes it

2Epic

Bulk-create the tickets under one epic, then add dependencies. Add only blocks edges, and only for real interface dependencies. Children of an epic are parallel by default; hierarchy is not ordering. The recurring beads failure is an agent encoding a sequence as a chain of blocks edges. Express constraints, not sequences.

br create -f plan.md --json                     # bulk import under the epic
br dep add <ticket> <depends-on> -t blocks        # interface dependency only
br ready --epic <epic-id> --json                # exactly what the loop will see

A review finding never reopens a closed ticket. A blocker becomes a bug ticket, child of the ticket whose owned paths it falls in, linked with discovered-from. The child inherits the parent's owned paths and acceptance checks, plus a check for the finding when the reviewer can state one, so the fix cannot regress what already passed. Because it is an ordinary open issue and br ready --epic is recursive, the same dispatch loop picks it up with no configuration. Closed tickets stay closed, and their close reasons stay true.

br create "Review: <finding>" -t bug --parent <ticket> --deps discovered-from:<ticket> -l review-finding
br update <bug> --design="<parent's owned_paths>" --acceptance-criteria="<parent's checks + fix check>"

3Orchestrate

The orchestrator is a program, not an agent. It holds no transcript and no state; state lives in br and git, and each pass starts from br ready --epic. Per ticket it claims, isolates, briefs, verifies in its own pane, merges, and closes. Where a decision needs judgment, the program calls a model once with a bounded input and a schema, then continues on the answer. The worker's own report of success is not evidence; the rerun in the verify pane is.

Where the loop calls a model

Three decisions, and only these three. Each is one call with a bounded input and a schema, made by the script and forgotten once it returns.

DecisionTriggerInputOutput
Stalled or workingNo pane output for five minutesThe last 80 lines of the paneworking or stalled
In-plan questionReport status is needs-humanThe question, the plan, the specAn answer, or route-to-human
Retry classVerification or the worker failsThe failing output and the ticketflaky, environment or defect, mapped to rerun, respawn or escalate

Decided by rules, never by a model: whether a worker is done or asking (the status field of its report file), which worktree is a ticket's (marker ancestry, then branch name, then the report file), which ticket a finding belongs to (owned-path match on the file:line), how many retries remain (once with the same worker, once with Opus 5, then escalate), merge order (the queue), and when the review loop stops (zero blockers, three rounds, or a round that changed nothing).

The merge queue

Merging is where parallel work actually integrates, so it is the most guarded step. Nothing merges until the suite passes in the ticket worktree after rebasing onto the integration branch. One team cut agent-caused merge failures by about 80 percent with that single rule.

4Watch

herdr reports one of five agent states: idle working blocked done unknown. Idle and done both mean ready for input. Unknown does not prove completion.

The caveat that shapes the worker contract. blocked fires only when herdr recognizes an approval or question UI. A worker that asks a question in prose finishes as done, so the agent state cannot tell finished from asking. The contract therefore requires the worker to write its structured report to .agent-report.json in the worktree before it stops. The loop reads that file and branches on its status field; no model is involved. Only when the file is missing does the loop fall back to agent read and a one-shot classifier call over the pane text.

SignalDefaultAction

5Review

Review happens at two levels. Per ticket, before the fast-forward: a fresh reviewer gets the ticket's diff against the integration branch, the rules, and the ticket's requirements, and the ticket does not close until a round returns zero blockers. Once the epic is integrated, one more review of epic/<id> against main looks for the cross-ticket conflicts that no single-ticket review can see, and anything it finds is filed as a bug child because every ticket is already closed.

  • Fresh context only. The reviewer gets the diff and the rules. It never sees the author's reasoning or transcript, and a reviewer told to find gaps will always find some, so it is told to flag only correctness and requirement gaps.
  • Every finding cites a rule and a file:line. Behavior claims without a citation are dropped.
  • Converge. After round one, nits are suppressed. Exit at zero blockers, cap at three rounds, and stop early when a round changes nothing.
  • A fresh worker fixes, never the reviewer. A blocker becomes a bug ticket, child of the ticket whose owned paths it falls in, with a discovered-from link and the parent's owned paths and checks. A blocker outside every ticket becomes a child of the epic for a human to scope. Warnings are recorded on the ticket. Closed tickets stay closed.

6Land

Under about 600 changed lines, open one pull request from epic/<id> to main. Above that, open stacked pull requests per ticket onto the integration branch with gh stack, three or four to a stack at most. The size rule comes from review data: PRs over 1,000 lines averaged 7.5 findings each, PRs under 50 lines averaged 0.5.

Landing has two more steps the original list did not have. First, ping the human through herdr notification show with the PR link, the review summary, and the token spend. Second, run one compound step: an agent writes the reusable lesson from this epic into the repo docs or the relevant CLAUDE.md, so the next plan starts from it.

Worker contract

A worker prompt is a self-contained brief. The worker never reads the epic, the plan, or another worker's transcript; everything it needs is in the brief, and everything it produces comes back in one structured report.

The brief carries

  • The ticket: title, description, design notes, acceptance criteria as runnable commands.
  • The epic chain: what this ticket exposes and which tickets consume it. Frozen for the run.
  • Owned paths as a hard boundary, and the single-writer paths it must not touch.
  • The test command, the commit prefix rule ([SPEC] or [BUG], enforced by the commit-msg hook), and the rule that apps run only through Docker Compose.
  • The return schema below, written to .agent-report.json in the worktree before the worker stops. The file is the primary channel; the pane is only the fallback.

The definition of done the worker cannot edit

  • Every acceptance check passes when the orchestrator reruns it.
  • The diff stays inside the owned paths.
  • No existing test is modified, skipped, or deleted. New tests are welcome.
  • Every commit is tested and carries the prefix.
{
  "status": "done | failed | needs-human",
  "ticket": "<id>",
  "commits": ["<sha>"],
  "checks": [{ "cmd": "<test command>", "result": "pass" }],
  "changed_paths": ["services/<module>/..."],
  "question": "only with needs-human: one question, stated so a yes or a choice unblocks it",
  "options": ["A", "B"],
  "unblock": "what the answer decides, and what stays unblocked meanwhile",
  "notes": "what the next worker in this worktree must know"
}

Guardrails

  • Verification lives outside the prompt. A hook or the orchestrator's rerun decides pass or fail, never the worker's summary. Both the compiler run and Grit saw agents game weak tests when the check was theirs to interpret.
  • Budget per epic. Log tokens per ticket as br comments, set a ceiling per epic, and stop dispatching when it is reached. Gas Town users report about 100 dollars an hour at peak.
  • One kill switch. One command stops every worker in the epic: iterate the panes, herdr agent send-keys <t> ctrl+c, and release the claims.
  • No orchestrator memory. If the orchestrator dies, a new one reads br and the worktrees and continues. Nothing it knows lives only in its context.
  • No new issues on a whim. Workers file nothing. The orchestrator files only the children the review loop produces, each with a discovered-from edge.

Not adopted

  • Gas Town itself. In maintenance mode, with reports of leaked tokens, killed crews and runs with permissions skipped. Borrow the integration branch, the merge queue, the watchdog that re-derives state, and the rule that hooked work must run.
  • Claude Code Agent Teams. Teammates share one checkout, cannot run headless, and cannot resume. The herdr shape, an external loop driving full sessions in isolated worktrees, is the Symphony shape.
  • Pure parallel. Isolation is cheap and integration is not. Parallelism is earned by disjoint owned paths declared in the plan, not assumed.
